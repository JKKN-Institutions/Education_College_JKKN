# JKKN Admin Panel — Complete Architecture & Implementation Plan
# Covers: Education, Pharmacy, Dental, Nursing, Arts & Science, AHS colleges
# One shared Supabase project. Each college is isolated by college_id.

================================================================================
PART 1 — THE BIG PICTURE
================================================================================

## What We're Building

Each JKKN college has:
  - A public-facing website:  education.jkkn.ac.in
  - An admin panel inside it: education.jkkn.ac.in/admin

The admin panel lives INSIDE the same Next.js project at the /admin route.
It connects to a SINGLE shared Supabase project used by all JKKN colleges.
Staff log in at /admin, manage content, and it appears instantly on the public site.

```
Supabase (One shared project for all JKKN colleges)
     │
     ├── education.jkkn.ac.in   (Next.js)  → /admin  ← Education staff only
     ├── pharmacy.jkkn.ac.in    (Next.js)  → /admin  ← Pharmacy staff only
     ├── dental.jkkn.ac.in      (Next.js)  → /admin  ← Dental staff only
     ├── nursing.jkkn.ac.in     (Next.js)  → /admin  ← Nursing staff only
     ├── artsscience.jkkn.ac.in (Next.js)  → /admin  ← Arts & Science staff only
     └── ahs.jkkn.ac.in         (Next.js)  → /admin  ← AHS staff only
```

Every college is a SEPARATE Next.js deployment. They all share the same
database, but each staff member can only see and manage their own college's
data. This is enforced at the database level via Row Level Security (RLS).


## How college_id Works (The Core Concept)

Every content table has a college_id column. It's just a text tag on each row.
Staff can create as many rows as they want — they all get tagged with their college.

  blogs table (real example):
  ──────────────────────────────────────────────────
  id   college_id    title                is_published
  1    education     "Teaching Methods"   true
  2    education     "Sports Meet Recap"  true
  3    education     "New Library"        true        ← unlimited rows
  4    pharmacy      "Drug Discovery"     true
  5    pharmacy      "Pharma Industry"    true        ← pharmacy's own rows
  6    dental        "Dental Camp"        true
  7    nursing       "Patient Care"       true

Education staff → see only rows where college_id = 'education'
Pharmacy staff  → see only rows where college_id = 'pharmacy'
No cross-contamination. No limits. They share one table but live in separate worlds.


## How the Current Deployment Knows Its college_id

Each Next.js project has a .env.local file:

  Education:  NEXT_PUBLIC_COLLEGE_ID=education
  Pharmacy:   NEXT_PUBLIC_COLLEGE_ID=pharmacy
  Dental:     NEXT_PUBLIC_COLLEGE_ID=dental
  Nursing:    NEXT_PUBLIC_COLLEGE_ID=nursing

All public queries filter by this value automatically.
All admin operations tag new rows with this value automatically.

PART 3 — AUTHENTICATION DESIGN

## Two Login Methods

/admin/login
├── "Sign in with Google" button   → Supabase Google OAuth
└── Email + Password form          → Supabase Email Auth


## Auth Flow

Staff opens education.jkkn.ac.in/admin
    ↓
middleware.ts checks: is user logged in? (Supabase session cookie)
    ↓ No                            ↓ Yes
Redirect to /admin/login     Check staff_profiles table
                                    ↓ No profile found    ↓ Profile exists
                               Show "Unauthorized"     Load admin dashboard
                               (wrong college)         (their college only)


## Who Can Register — Three Options

### Option A: Open Registration (Anyone with the link can register)
Staff go to /admin/login → click "Sign up" → enter email + password
Account created instantly. They can immediately do CRUD.
RISK: Anyone who finds the URL can create an account.

### Option B: Invite-Only via Supabase Dashboard (Recommended for now)
Developer adds staff emails in the Supabase Auth dashboard.
They receive an email invite, set their password.
Google login works for their Google Workspace email too.
BENEFIT: Only people you explicitly add can access.

### Option C: Domain-Restricted Google Auth
Only @jkkn.ac.in Google accounts can log in.
Auto-blocked for anyone outside the institution.
BENEFIT: Maximum security with zero manual management.

RECOMMENDATION: Start with Option B (invite-only). Switch to Option C later
when all staff have @jkkn.ac.in email addresses.


## Staff Profiles Table (Links auth user → college)

After a user authenticates with Supabase Auth, a row in staff_profiles
tells the system which college they belong to.

  staff_profiles table:
  ──────────────────────────────────────────────────────────────
  id (uuid)         = auth.users.id (matches Supabase Auth user)
  college_id        = 'education' | 'pharmacy' | 'dental' | etc.
  full_name         = "Priya Kumar"
  role              = 'staff' | 'admin' (for future role expansion)
  is_active         = true/false (disable access without deleting)
  created_at        = timestamptz

How it works:
  1. Developer creates user in Supabase Auth dashboard (invite-only)
  2. Developer manually inserts row in staff_profiles:
       INSERT INTO staff_profiles (id, college_id, full_name, role)
       VALUES ('auth-user-uuid', 'education', 'Priya Kumar', 'staff');
  3. Staff receives email invite, sets password, logs in
  4. System reads their staff_profiles row → knows they are 'education' staff
  5. All their content is automatically tagged college_id = 'education'
  6. They only see rows where college_id = 'education'

PART 5 — SUPABASE STORAGE BUCKETS
================================================================================

One set of buckets shared across all colleges. College isolation is achieved
by using college_id as a path prefix inside each bucket.

Supabase Storage (shared jkkn project)
├── event-images/              Public read, authenticated write
│   └── {college_id}/{year}/{slug}-cover.jpg
│       e.g., education/2025/annual-day-cover.jpg
│       e.g., pharmacy/2025/pharma-fest-cover.jpg
│
├── blog-images/               Public read, authenticated write
│   └── {college_id}/{year}/{slug}-cover.jpg
│
├── gallery/                   Public read, authenticated write
│   └── {college_id}/{album-slug}/{filename}.jpg
│       e.g., education/sports-day/photo1.jpg
│       e.g., pharmacy/industry-visit/photo1.jpg
│
├── faculty-photos/            Public read, authenticated write
│   └── {college_id}/{faculty-id}.jpg
│
└── notice-attachments/        Public read, authenticated write
    └── {college_id}/{year}/{filename}.pdf

Storage Rules:
- Public read:         The website fetches images without authentication
- Authenticated write: Only logged-in staff can upload
- Authenticated delete: Only logged-in staff can delete files
- File size limit:     5MB for images, 10MB for PDFs
- Path prefix enforced by upload code (college_id from staff_profiles)

PART 6 — ROW LEVEL SECURITY (RLS) POLICIES
================================================================================

RLS runs at the Postgres level — it is the enforcement mechanism.
No matter what the application code does, Postgres enforces these rules.

────────────────────────────────────────────────────────────────────────────────
Public Website (Unauthenticated reads)
────────────────────────────────────────────────────────────────────────────────

These policies let the public website read published content for its college.
The college_id filter in application code matches NEXT_PUBLIC_COLLEGE_ID.

-- events: public can read published events
CREATE POLICY "public_read_events" ON events
  FOR SELECT USING (is_published = true);

-- blogs: public can read published blogs
CREATE POLICY "public_read_blogs" ON blogs
  FOR SELECT USING (is_published = true);

-- gallery_albums: public can read all albums
CREATE POLICY "public_read_gallery_albums" ON gallery_albums
  FOR SELECT USING (true);

-- gallery_images: public can read all images
CREATE POLICY "public_read_gallery_images" ON gallery_images
  FOR SELECT USING (true);

-- notices: public can read active, non-expired notices
CREATE POLICY "public_read_notices" ON notices
  FOR SELECT USING (
    is_active = true AND
    (expires_at IS NULL OR expires_at > now())
  );

-- faculty: public can read active faculty members
CREATE POLICY "public_read_faculty" ON faculty
  FOR SELECT USING (is_active = true);

Note: The application code ALSO filters by college_id on every query.
RLS allows the read; the query filter narrows it to the right college.

────────────────────────────────────────────────────────────────────────────────
Admin Panel (Authenticated staff — full CRUD, own college only)
────────────────────────────────────────────────────────────────────────────────

Staff can only read/write rows that match THEIR college_id from staff_profiles.

Helper function (used in all policies below):
-- Returns the college_id of the currently logged-in staff member
CREATE OR REPLACE FUNCTION get_my_college_id()
RETURNS text AS $$
  SELECT college_id FROM staff_profiles WHERE id = auth.uid()
$$ LANGUAGE sql SECURITY DEFINER;

-- events: staff can do all CRUD on their own college's events
CREATE POLICY "staff_all_events" ON events
  FOR ALL USING (college_id = get_my_college_id())
  WITH CHECK (college_id = get_my_college_id());

-- blogs: staff can do all CRUD on their own college's blogs
CREATE POLICY "staff_all_blogs" ON blogs
  FOR ALL USING (college_id = get_my_college_id())
  WITH CHECK (college_id = get_my_college_id());

-- gallery_albums: staff can manage their college's albums
CREATE POLICY "staff_all_gallery_albums" ON gallery_albums
  FOR ALL USING (college_id = get_my_college_id())
  WITH CHECK (college_id = get_my_college_id());

-- gallery_images: staff can manage images inside their college's albums
CREATE POLICY "staff_all_gallery_images" ON gallery_images
  FOR ALL USING (
    EXISTS (
      SELECT 1 FROM gallery_albums
      WHERE gallery_albums.id = gallery_images.album_id
      AND gallery_albums.college_id = get_my_college_id()
    )
  );

-- notices: staff can manage their college's notices
CREATE POLICY "staff_all_notices" ON notices
  FOR ALL USING (college_id = get_my_college_id())
  WITH CHECK (college_id = get_my_college_id());

-- faculty: staff can manage their college's faculty
CREATE POLICY "staff_all_faculty" ON faculty
  FOR ALL USING (college_id = get_my_college_id())
  WITH CHECK (college_id = get_my_college_id());

-- staff_profiles: staff can read their own profile only
CREATE POLICY "staff_read_own_profile" ON staff_profiles
  FOR SELECT USING (id = auth.uid());

What this means in practice:
- Education staff → can ONLY see/edit rows where college_id = 'education'
- Pharmacy staff  → can ONLY see/edit rows where college_id = 'pharmacy'
- Cross-college access is IMPOSSIBLE — blocked at database level
- Staff cannot change their own college_id (only developer can)

PART 11 — DATA FLOW DIAGRAMS
================================================================================

## Staff Adds New Content

Staff at /admin/events/new
    ↓ fills form + uploads image
    ↓
Image upload → Supabase Storage (path: education/2025/annual-day-cover.jpg)
    ↓ returns public URL
Form submit → Supabase DB INSERT into events
    (college_id = 'education', title = ..., image_url = ..., is_published = true)
    ↓
RLS confirms: college_id matches staff's college → INSERT allowed
    ↓
Server Action calls revalidatePath('/events') → Next.js ISR clears cache
    ↓
/events page rebuilds with new event instantly


## Public Visitor Reads Content

Visitor opens education.jkkn.ac.in/events
    ↓
Next.js fetches from Supabase:
    SELECT * FROM events
    WHERE college_id = 'education'        ← from NEXT_PUBLIC_COLLEGE_ID
    AND is_published = true
    ORDER BY event_date DESC
    ↓
RLS: public_read_events policy allows SELECT (is_published = true)
    ↓
Pharmacy data is also in the table but NEVER returned
(filtered by college_id in the query)
    ↓
Page renders with only Education events


## Cross-College Isolation (What Happens if Someone Tries)

Education staff tries to read pharmacy data:
    SELECT * FROM events WHERE college_id = 'pharmacy'
    ↓
RLS: staff_all_events policy checks get_my_college_id() = 'education'
     'pharmacy' ≠ 'education'
    ↓
Returns empty result. No error. No data. Complete isolation.

PART 14 — MIDDLEWARE FOR ROUTE PROTECTION
================================================================================

A single middleware.ts file at the project root protects all /admin/* routes.

Incoming request to /admin/**
    ↓
middleware.ts checks Supabase session cookie
    ↓ No session                    ↓ Valid session
Redirect to /admin/login     Check staff_profiles table
                                    ↓ No profile          ↓ Profile found
                              Redirect /admin/login    Allow through
                              (not authorized staff)   (admin page loads)

/admin/login is the ONLY admin route that works without authentication.

The middleware also:
- Refreshes the Supabase session cookie on every request
- Handles OAuth callback redirects (for Google login)
- Excludes public routes like /events, /blogs, /gallery from protection


================================================================================
PART 15 — ISR (INCREMENTAL STATIC REGENERATION) STRATEGY
================================================================================

Public pages use ISR — fast like static pages, auto-refresh when data changes.

Public Page              Revalidate Every    Reason
───────────────────────────────────────────────────────────────────────────
/events (listing)        60 seconds          Events added regularly
/events/[slug]           300 seconds         Individual events rarely change
/blogs (listing)         60 seconds          New posts added regularly
/blogs/[slug]            300 seconds         Blog content rarely changes
/gallery                 300 seconds         Gallery updated in batches
/notices                 30 seconds          Notices are urgent
/others/faculty-details  3600 seconds        Faculty rarely changes

On-demand revalidation:
When staff clicks "Publish" in the admin panel, a Server Action calls
revalidatePath('/events') — the page rebuilds instantly without waiting
for the timer. Staff sees the change live immediately after publishing.

PART 17 — APPLYING THIS PLAN TO ANOTHER COLLEGE (e.g., Pharmacy)
================================================================================

When setting up pharmacy.jkkn.ac.in (or any other JKKN college):

Step 1: Database — NO changes needed
  - All tables already have college_id column
  - All RLS policies already work for any college_id value
  - Just create a staff_profiles row with college_id = 'pharmacy'

Step 2: Storage — NO changes needed
  - Path conventions already use {college_id} prefix
  - pharmacy/ folder created automatically on first upload

Step 3: New Next.js project for pharmacy
  - Copy the Next.js project structure (or use a template)
  - Change .env.local: NEXT_PUBLIC_COLLEGE_ID=pharmacy
  - The same Supabase URL and anon key as education

Step 4: Create pharmacy staff account
  - Go to Supabase Auth dashboard
  - Invite pharmacy staff member's email
  - Insert into staff_profiles: (id=their-uid, college_id='pharmacy', ...)

That's it. Pharmacy staff can now log in, manage their content, and
they will NEVER see education data. Zero code changes required.

Valid college_id values (confirmed JKKN colleges):
  education    → Education College      → education.jkkn.ac.in
  pharmacy     → Pharmacy College       → pharmacy.jkkn.ac.in
  dental       → Dental College         → dental.jkkn.ac.in
  nursing      → Nursing College        → nursing.jkkn.ac.in
  artsscience  → Arts & Science College → artsscience.jkkn.ac.in
  ahs          → AHS College            → ahs.jkkn.ac.in

PART 18 — SCALE PROOF (How Multiple Rows Work Per College)
================================================================================

The college_id column is just a tag — not a limit.
Staff create as many rows as they want.

Feature                           Supported?    Limit?
──────────────────────────────────────────────────────
Multiple blogs per college        Yes           No limit
Multiple events per college       Yes           No limit
Multiple gallery albums           Yes           No limit
Multiple photos per album         Yes           No limit
Multiple notices per college      Yes           No limit
Multiple faculty per college      Yes           No limit
Staff adding content independently Yes          No conflict
One college seeing another's data No            Blocked by RLS

Education staff add 1000 blogs → all get college_id = 'education'
Pharmacy staff add 500 blogs  → all get college_id = 'pharmacy'
Same table. No conflict. No cross-contamination.
